层级串联叙述

任务层要求在城市 ODD 内把乘客从 A 点安全送到 B 点；体系层由车队、云控平台、高精地图与 V2X 共同保障任务可持续运营；整机层把感知决策结果转化为可执行的车辆运动；本系统（线控底盘平台）是"意图"到"车轮"之间的最后执行环节，把上层下发的目标横摆/减速度/驱动力矩转化为四轮与转向机构的真实运动；子系统层由转向、制动、驱动、悬架、域控与安全监控六条链路分工实现；模块层则是电机、传感器、控制器、阀类等可采购、可验证的物理件。任一层失效都会沿层级向上影响任务，因此线控底盘必须在子系统与模块层面做到故障可检测、降级可运行。

二、业务需求规格说明（BRS）依据 ISO/IEC/IEEE 29148:2018 表4-1

1. 简介

1.1 业务目的

出行运营企业需要在限定 ODD 内部署 L4 级无人车队以降低人工驾驶成本、提升运营安全与准点率。传统机械/液压底盘无法直接接收电子控制指令，也不具备双冗余与故障降级能力，无法支撑 L4 级自动驾驶"驾驶员缺失"场景。本业务旨在构建一套标准化、可跨车型复用的线控底盘平台，作为整车厂与自动驾驶公司之间的通用执行底座，缩短新车型开发周期、降低单车开发成本。

1.2 业务范围

  • a) 业务域：自动驾驶车辆底盘开发与供应链业务域。
  • b) 业务活动范围：线控底盘平台的需求定义、开发验证、量产交付、在役运维与 OTA 升级；覆盖整车厂（OEM）、自动驾驶公司（AD Supplier）、底盘零部件供应商三方协同。
  • c) 系统范围：本提案系统为"线控底盘平台"，不含自动驾驶感知/决策算法、不含车身内外饰；与两者之间通过标准车载接口（CAN/Ethernet、AEB/横纵向控制报文）交互。

1.3 业务概况

业务上游为 OEM 的整车项目与 AD 公司的自动驾驶栈；中游为本线控底盘平台（含 6 大子系统）；下游为充电运维场站与云控监控平台。外部监管包括 GB 自动驾驶汽车相关标准、ISO 26262 功能安全、ISO 21448 SOTIF、UN R155/R156 网络安全与软件升级。

1.4 定义

  • 线控（By-wire）：以电信号代替机械/液压连接来传递控制指令的底盘控制方式。
  • ODD：设计运行范围（Operational Design Domain）。
  • EMB：电子机械制动（Electro-Mechanical Brake）。
  • ConOps / OpsCon：运营概念 / 运行概念。

1.5 主要相关方

详见第三节相关方列表。主要相关方包括：OEM 整车项目组、自动驾驶供应商、乘客、车队运营方、远程接管安全员、底盘零部件供应商、交通监管与认证机构、保险与法务方、售后服务网络。

3. 业务管理需求

3.1 业务环境

外部环境：L4 政策试点扩围、Robotaxi 商业化提速、线控底盘为强制性技术门槛；内部环境：企业已有机械底盘产线，需新建 EMB/SBW 装配与标定能力；技术基础：车载以太网、区域控制器、AUTOSAR Adaptive 已成熟。

3.2 使命、目的与目标

使命：成为 L4 无人车可信赖的执行底座。三年业务目标：平台覆盖 ≥3 款车型、累计装配 ≥10000 台、重大安全事故率为 0、单车开发周期缩短 30%。

3.3 业务模型

向 OEM 按平台授权+按车收费；向 AD 公司提供标准接口与联合标定服务；后市场提供 OTA 订阅、健康度预测与备件服务。

3.4 信息环境

统一底盘数据字典与信号矩阵；与企业整车 PLM、ALM 打通；在役车辆底盘状态数据回传云控平台用于预测性维护。

4. 业务运行需求

4.1 业务过程

核心业务流程：需求冻结 → 平台开发 → 台架/整车验证 → SOP 量产 → 在役监控 → OTA 迭代 → 报废回收。

4.2 业务运营策略与规则

  • B-RULE-01：任何影响安全的需求变更必须经 FMEA/FTA 复审后方可发布。
  • B-RULE-02：OTA 升级必须满足 UN R156 要求，分批次灰度、可回滚。

4.3 业务运行约束

平台必须在 -40℃~+85℃ 车规环境下工作；指令响应到执行输出端的总延迟 ≤ 50 ms；关键链路必须双冗余。

4.4 业务运行质量

底盘平台可用性 ≥ 99.99%；平均无故障里程 ≥ 10000 km；乘客体感横向加速度波动 ≤ 0.05 g。

4.5 业务结构

平台按转向/制动/驱动/悬架/域控/安全六个事业部横向开发，与 OEM 项目组按纵向矩阵对接。

5. 提案系统初步运行概念

5.1 初步运行概念（ConOps 摘要，详见第五节）

系统在 L4 模式下完全由自动驾驶域控下达指令，驾驶员不在环；在最小风险状态（MRM）下由本平台自主执行靠边停车。支持三种运行模式：全自动驾驶、人工应急接管（带可恢复方向盘/踏板）、维保模式。

5.2 初步运行场景

  • 场景 S-01：城市道路跟车起步—巡航—停车，底盘平滑响应目标加速度。
  • 场景 S-02：高速紧急避险，底盘在 100 ms 内执行最大制动+横向避让。
  • 场景 S-03：单一传感器/执行器失效，系统 200 ms 内切换冗余通道并降级至最低风险状态。

6. 其他初步生存周期概念

采办：与 Tier1 联合开发；部署：随整车 SOP 上线；支持：4S 店+移动维保车；弃置：高压件回收、ECU 数据擦除。

7. 项目约束

预算 ≤ 4.5 亿元；2027 年 SOP；平台必须兼容现有纯电底盘产线。

4. 系统运行需求

4.1 系统过程

底盘平台实时执行：传感器采样 → 域控融合决策 → 横/纵/垂向力矩分配 → 执行器动作 → 状态回读闭环，周期 10 ms。

4.2 系统运行策略与规则

  • 指令合法性校验：任何超 ODD/超物理边界的指令必须拒绝并上报。
  • 失效优先级：执行器失效 > 传感器失效 > 通信失效，按最高等级触发 MRM。

4.3 系统运行约束

横向跟踪误差 ≤ 0.2 m；纵向停车距离误差 ≤ 0.1 m；端到端延迟（指令到轮端）≤ 50 ms；EMB 建压时间 ≤ 150 ms。

4.4 系统运行模式与状态

模式描述退出条件
M1 全自动驾驶完全由自动驾驶栈控制，无人员在环ODD 退出/系统故障/乘客按急停
M2 远程接管云驾舱下发遥控指令，底盘按比例执行远程连接中断 > 3 s
M3 最小风险 MRM自主减速靠边停车、双闪、上报车辆静止且通知完成
M4 维保模式限速 5 km/h，允许诊断仪接入退出维保工位

五、运营概念 ConOps（Concept of Operations）

ConOps 站在运营企业视角，回答"这套系统将如何被用来做生意"。

运营政策与约束

  • 仅在已公示 ODD（城市核心区、指定天气与光照）内开放付费载人。
  • 每 10 台车配置 1 名远程安全员，7×24 小时值班。
  • 任何 ASIL-D 故障车辆必须立即退出运营队列。

系统描述

线控底盘平台作为整车"执行底座"，向上提供标准横纵向控制接口，向下驱动转向/制动/驱动/悬架执行器，并自带冗余与安全监控。

运行模式

M1 全自动 / M2 远程接管 / M3 最小风险 / M4 维保，状态机见 StRS 4.4。

用户类型

乘客（无驾驶权）、远程安全员、维保技师、OEM/AD 开发工程师。

支持环境

云控平台 + 高精地图 + V2X 路侧单元 + 充换电站 + 移动维保车队。

六、运行概念 OpsCon（Operational Concept）

OpsCon 站在车辆/系统本身视角，描述一次具体任务从上车到下车全过程中底盘如何动作。
